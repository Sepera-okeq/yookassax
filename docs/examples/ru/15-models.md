# Модели ответов

Каждый объект, который приходит от API, разбирается в типизированную модель.
Словарей в ответах не остаётся: `dict` встречается только там, где произвольное
содержимое обещает сама спецификация (`metadata`, `holder`).

Всего моделей: 73. Полнота держится тестами: `test_every_response_object_has_a_model`
проверяет, что у каждого объекта из ответов есть модель, а
`test_models_cover_documented_fields` - что в модели описаны все поля этого
объекта из спецификации. Новый объект или поле в спецификации валит прогон,
пока их не опишут.

## Как читать таблицы

«Полей» - сколько полей у модели, включая унаследованные, кроме служебного
`raw`. Неизвестное поле не теряется: оно остаётся в `raw`, доступно через
`extra()` и один раз даёт `UnknownFieldWarning`.

## Чего специально нет

**Моделей тел запросов.** Тело создаётся словарём: он принимает новые поля API
сразу, а не после обновления библиотеки. В спецификации это схемы с суффиксом
`Data` и `Request` - `PaymentMethodDataBankCard`, `PayoutRequest` и подобные.

**Отдельных классов на каждую схему-синоним.** У ЮKassa одинаковые по форме
объекты названы по-разному в каждом ресурсе: `SettlementPaymentItem`,
`SettlementRefundItem`, `SettlementPayoutPayment` - это одно и то же
`{type, amount}`. Такие схемы сведены в одну модель, соответствие записано в
тесте `SCHEMA_TO_MODEL`.

**Моделей ошибок.** Ответ с ошибкой поднимается исключением, а не возвращается
объектом: `BadRequest`, `Forbidden` и остальные несут `code`, `description`,
`parameter` и `request_id`.
